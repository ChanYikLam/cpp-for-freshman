0001 · 你的第一个 C++ 程序

你的第一个 C++ 程序

本节目标：走通「写源文件 → 编译 → 运行 → 看懂报错 → 改对」这条循环，让终端打印出一行 Hello。

这节课从一屏红字讲起

很多人学编程的第一天，是照着别人给的例子敲下一段代码，然后 g++ 甩回一屏红字。这一课不先讲 C++ 是什么，先把那屏红字变成一行输出。

一条循环：从文本到程序

先讲清楚一件事：为什么写程序要先准备一个纯文本文件。

计算机的处理器只认识一串串由 0 和 1 组成的指令，那套东西叫机器指令。人几乎不可能直接写机器指令，写完也读不懂。于是人们退一步：用一种人看得懂的写法把要求写下来，再让一个程序把它翻译成机器指令。这个「人看得懂、机器看不懂」的文本文件，就是源文件（source file）；C++ 的源文件习惯以 .cpp 结尾。把源文件翻译成机器能执行的指令，这个翻译过程叫编译（compile）。

一份稍大的程序会被拆成好几个源文件，翻译完还会用到现成的代码。把编译产生的若干目标文件，以及程序用到的标准库代码，拼装成一个完整程序，这个过程叫链接（link）。链接完成后得到的、可以直接运行的产物，就是可执行文件（executable）。你双击它、或者在终端里敲它的名字，它就跑起来。

对写代码的人来说，这三件事是连在一起的一条循环：

编译之所以需要单独一个程序，是因为翻译这件事必须有人替你做：机器不认识 std::cout，只认识机器指令；编译器（compiler）就是干这个翻译的现成工具。本课程用到的编译器是 g++。

写第一份源文件

新建一个文本文件，内容如下。存成 intro-01.cpp，再编译。

#include <iostream>

int main()
{
    std::cout << "Hello" << std::endl;
    return 0;
}

先看懂每一部分在干什么，暂时不用记住细节：

写法它在做什么
#include <iostream>把名字叫 iostream 的头文件借进来。输入输出要用到的名字都写在这个文件里
int main()每个 C++ 程序都有且只有一个 main，程序从这里开始执行
{ 与 }一对花括号圈出一个范围，main 要执行的东西写在里面
std::cout << "Hello" << std::endl;把 Hello 送到终端，再换一行
return 0;告诉系统「我正常结束了」。0 表示一切正常

头文件（header file）是为「名字太多、要分类」准备的。标准库里的现成代码有成百上千个名字，全部堆在一起查找困难，官方就把它们按用途切开，每个文件管一类。要比方的话，它更像一份「这些名字在这里」的清单：#include <iostream> 的意思是把 iostream 这份清单拿进来，好让编译器认识 std::cout。

std:: 是名称空间（namespace）限定的写法。标准库的作者担心自己起的名字（比如 cout）和你的名字撞车，于是把所有标准库名字都放进一个叫 std 的柜子里。std::cout 读作「std 柜子里的 cout」，撞名就不会发生了。

每次都写 std:: 太累：using namespace std;

上一段那个写法完全正确，但你能看出来：cout、endl、后面要学的 cin，每用一个就要在它前面写一遍 std::。一行里出现两个，就得写两遍。

所以实际写代码时，几乎所有人都会在文件开头加一行声明，意思是「下面我用到的名字，先到 std 这个柜子里找」。把刚才那份存成 intro-02.cpp：

#include <iostream>

using namespace std;      // 以后写 cout 就等于写 std::cout

int main()
{
    cout << "Hello" << endl;
    return 0;
}

这一行加进去之后，从它下面开始，cout 和 std::cout 指的是同一个东西。本课程后面所有的代码都用这种写法，你照着敲就行。

两种写法你会同时见到，都不是错的

别人的代码里三种写法都常见：std::cout（全写限定名）、cout + 开头 using namespace std;（本课程用这种）、以及 using std::cout;（只打开一个名字）。

它们指的是同一个东西，你看到任何一种都不要慌。本课程统一用第二种：少打字，又不至于把一大柜子名字全打开。你现在只要记住一件事——这一行要写在 #include 之后、main 之前，写漏了编译器会说 cout 未声明，那就是忘了它。

语句（statement）是一条完整的指令，C++ 里以分号结尾。程序就是按顺序执行的一条条语句——这解释了为什么下面那个反例里的分号那么要紧。

编译、运行、看到 Hello

在存放 intro-01.cpp 的目录下打开终端，敲这条命令：

g++ intro-01.cpp -o first

命令读法是：用 g++ 编译 intro-01.cpp，产物叫 first。-o 是 output（输出）的缩写，-o first 就是「输出的文件叫 first」。编译期间没有任何输出，就是成功了——这一条要记牢：编译器的风格是没有消息就是好消息。

接着运行它。注意前面的 ./：

$ ./first
Hello

./first 的意思是「运行当前目录下的 first」。只敲 first 系统会去别的地方找，通常找不到，然后回你一句 command not found。

不加 -o 会怎样

如果敲的是 g++ intro-01.cpp，编译一样成功，只是产物叫 a.out，运行要敲 ./a.out。-o 的作用就是给产物起个好认的名字：你编了 first、average、grade 三个程序，桌面上三个 a.out 会互相覆盖，谁也分不清谁。本课程统一用 g++ 源文件.cpp -o 程序名。

顺带一句命名上的讲究：源文件叫 intro-01.cpp，产物叫 first，两者不同名。它们本来就是两样东西——一个是给你读的文本，一个是给机器执行的程序——名字分开，ls 列目录时一眼就分得清哪个是哪个。

macOS 上看到 Apple clang，是正常的

在终端敲 g++ --version，输出第一行是 Apple clang version 17.0.0，不是 "GCC"。这不是装错了：macOS 自带的 /usr/bin/g++ 一路指向苹果的编译器 clang，它照样按 C++ 标准编译你的代码。这一套课程里凡是说 g++ 的地方，照敲就行。

macOS 上编译器的安装方式是 xcode-select --install（本机不需要单独装 GCC）。装好之后敲 xcode-select -p，会打印出编译工具所在的路径，比如 /Library/Developer/CommandLineTools；能打印出路径就说明装好了。Linux 上则用发行版的包管理器装 gcc-c++ 或 build-essential，那里的 g++ 是真 GCC（GCC 官方文档写明：编译 C++ 程序时用 g++ 而不是 gcc）。

一屏红字怎么读

现在把示例改成下面这样。这一份少了一个分号，是故意留错的反例，存成 broken-intro-01.cpp 试试。

#include <iostream>

int main()
{
    std::cout << "Hello" << std::endl
    return 0;
}

编译它，屏幕上会出现这样一屏：

broken-intro-01.cpp:5:38: error: expected ';' after expression
    5 |     std::cout << "Hello" << std::endl
      |                                      ^
      |                                      ;
1 error generated.

逐行拆开看。第一行是全部信息里最要紧的一行，它由五段拼成：

片段含义
broken-intro-01.cpp出问题的文件
5第 5 行
38第 38 列，也就是第二行里 ^ 指着的那个位置
error严重程度：error 会导致编译失败，warning 只是提醒
expected ';' after expression编译器的话：这个表达式后面应该有个分号

第二行把那第 5 行原文抄给你看，第三行的 ^ 指着它发现问题的那一列。第四行 ; 是它顺手给你的建议——它认为这里该补一个分号。最后一行 1 error generated. 是统计。

这一屏要看的信息其实就三样：哪个文件、哪一行、它认为哪里不对。编译器打印的这类信息有个正式叫法叫诊断消息（diagnostic message）。Learn C++ 讲这一处时的说法是：诊断消息里通常带着编译器发现问题的文件名和行号，再加一句「它期望什么、实际碰到什么」；而真正的问题可能就在那一行，也可能在前一行。

编译器不同，这几行的样子会变

C++ 标准没有规定诊断消息该怎么分类、怎么措辞。同一份代码，不同编译器给出的字句和排版都可能不一样：

  • 列号不一定有。上面这一屏里有 5:38，冒号后面那个 38 就是列号，有些编译器会给，有些只给到行号。
  • 抄出原文的那几行、^、以及最后一行替你写好的建议，都可能没有，只留一句纯文字的诊断消息。
  • 统计那一行的写法各地不同。Visual Studio 会给每个问题一个编号，写成 error C2143 这样；GCC 与 Clang 的口径也不一样。

所以真正稳定的只有一条：诊断消息里带着文件名和行号。其余的都是锦上添花，你的编译器给多少就用多少。

学长的建议在这里很实用：看到报错先别慌，按这条顺序来。

  1. 从诊断消息里找出文件名与那个行号；
  2. 看那一行，再看它上下周围的几行，找拼写错误或者漏掉的东西；
  3. 顺手确认一件事：代码里没有混进编辑器显示的行号数字（那行号是编辑器画上去的，不该出现在文件内容里）；
  4. 改完重新编译一次，看那条消息还在不在——诊断消息一条一条消掉，就是编译在往前走。
报错的行号常不是真正错的那一行

^ 指着 std::endl 的末尾，可这一行本身读起来并没有毛病。原因是编译器读到这一行末尾时，原本在等一个分号，结果等来的是下一行的 return，于是它判定「这个表达式还没结束」——报的是它意识到不对的位置，而分号漏在了它刚读完的那一行。

这就是上面第 2 步里「再看它上下周围的几行」为什么不是客套话：真正的问题可能就在它指的那一行，也可能在前一行。C++ 里漏分号几乎都是这个形状。

改对一个，再看下一个，这也是常态。把第 5 行末尾补上分号、第 6 行故意不补，得到 broken-intro-02.cpp：

#include <iostream>

int main()
{
    std::cout << "Hello" << std::endl;
    return 0
}
broken-intro-02.cpp:6:13: error: expected ';' after return statement
    6 |     return 0
      |             ^
      |             ;
1 error generated.

结构一模一样，只是换到了第 6 行。这就是编译器的工作方式：它一次只报它最先撞上的那个问题，不会替你把所有错误一次挑完。修一个、编一次、再看下一个，是正常节奏，不是笨。

改一次、编一次、跑一次

修好第 6 行，再编译、再运行，Hello 就出来了。然后试试改内容：

g++ intro-01.cpp -o first && ./first

&& 的意思是「前一条成功了再做后一条」，可以省掉一次敲命令。把 "Hello" 改成 "Hello, GDMU"，存盘，重新编译运行，输出就变了。每次改了源文件都必须重新编译——编译产物是上一次源文件翻译出来的成品，源文件改了它不会自己更新。

改了没保存，跑出来还是旧的

最常见的假 bug：代码改了、编译了、运行了，输出还是老样子。查一下编辑器标题栏有没有一个小圆点，有就是没存盘。编译读到的是硬盘上的文件，编辑器里那点改动还在内存里。

再练一件必须会的事：分清哪一行是谁说的。运行程序时终端上出现的文字，都是你的程序打印的；编译时出现的 error、warning、note 那些行，都是编译器打印的，你的程序那时候还没生成，根本没机会说话。一眼分清这个，后面排错会省很多力气。

轮到你走一遍

看别人敲和亲手敲，差别在这一节。刚才示范的那份源文件在 code/intro-01.cpp，你自己那份写完可以对着它比一比。

上手做 从空白文件到 Hello

第 1 步 · 自己建一份。新建一个文本文件，敲进前面那份 intro-01.cpp 的内容，存成 myfirst.cpp（文件名由你定，.cpp 结尾就行）。

第 2 步 · 编译运行。在存放这个文件的目录下敲（产物名换成你自己的）：

g++ myfirst.cpp -o myfirst && ./myfirst

看到这一行，循环就跑通了：

$ ./myfirst
Hello

把引号里的字换成你自己的名字或学号，存盘、重新编译、再看一次。改了源文件必须重新编译，这一步你刚亲眼验证过。

第 3 步 · 故意改坏它。把 std::endl 后面那个分号删掉，再编译。屏幕会还你一屏红字：

myfirst.cpp:5:38: error: expected ';' after expression
    5 |     std::cout << "Hello" << std::endl
      |                                      ^
      |                                      ;
1 error generated.

按前面教的顺序读它：哪个文件、哪一行、它认为缺了什么。这一屏会指出第 5 行，而 ^ 指在行尾——分号确实就是漏在那里，这一回编译器指对了。你那份报错里的行号可能和这里不一样（前面多一行注释、或者消息措辞不同），按它给的行号去找就行。

第 4 步 · 改回来。把分号补上，重新编译运行，Hello 又回来了。

走到这里，你已经独立走完了「写源文件 → 编译 → 运行 → 看懂报错 → 改对」这一整条循环。后面每一课都在这个循环里加新东西，这条循环本身不会变了。

想装到 Windows 上

前面用的是命令行。Linux 上打开终端就能用 g++，macOS 上装好命令行工具也有；Windows 上多两步：Windows 本身不带 g++，要自己装一套带 GCC 的工具链；而且课程用的是命令行，Windows 上得有地方敲命令。

推荐路径：VS Code + MSYS2。两者都在积极维护，装完之后敲的命令和前几节完全一致。

第一步，装 MSYS2：从 msys2.org 下载安装包并运行（需要 64 位 Windows 10 1809 或更新）。安装完成后它会自动打开一个终端窗口。

第二步，在这个终端里装 GCC。VS Code 官方文档给的是完整工具链这一条：

pacman -S --needed base-devel mingw-w64-ucrt-x86_64-toolchain

中途问 Proceed with installation? 时按回车、看到要 Y 的地方敲 y。装完可以敲 g++ --version 确认能打印出版本号。

第三步，装 VS Code 并加 C/C++ 扩展。VS Code 本身只是编辑器，它靠扩展认识 C++。在 VS Code 里按 Ctrl+Shift+X 打开扩展面板，搜 C++ 装上微软那个 C/C++ 扩展即可。

MSYS2 官方还给了更小的一条安装命令 pacman -S mingw-w64-ucrt-x86_64-gcc，只装编译器。两条都能用，官方 VS Code 教程推荐前者，因为它把调试器也一起装上了。

装好之后，后面每一节的命令照敲：

g++ intro-01.cpp -o first
Windows 上敲命令的几个小差别
  • 运行程序敲 first.exe 或 .\first.exe（Windows 用反斜杠加一个点表示当前目录，对应 macOS 的 ./）。
  • 终端建议用 PowerShell 或 MSYS2 的那个终端窗口，不用 Windows 自带的 cmd 也行。
  • 如果敲 g++ 提示「不是内部或外部命令」，是第 2 步装出来的 bin 目录没进系统的 PATH——VS Code 官方教程里「Add the path of your ucrt64 bin folder to the Windows PATH」那几步讲的就是这件事（默认目录是 C:\msys64\ucrt64\bin）。
如果你已经在用 Dev-C++

Dev-C++ 的官方下载渠道已经失效（原站连不上、SourceForge 上的项目页也打不开），而它本身已经很多年不再维护了——Learn C++ 的 IDE 选择那一节把它列进了「应当避免的 IDE」。这些都不影响你继续用它：它里面打包的编译器能正常按 C++ 标准编译本课程的全部代码，你只需要把「命令行里做的」和「Dev-C++ 里点的」对上。

命令行里做的Dev-C++ 里点的
新建 intro-01.cpp文件 → 新建 → 源代码，写完按 Ctrl+S 存成 .cpp
g++ intro-01.cpp -o first按 F11（编译并运行），或点工具栏上那个「编译运行」按钮
./first 看输出F11 之后自动弹出一个黑色控制台窗口，输出就在里面
看报错窗口下方那一栏，双击报错行会跳到出问题的代码行

上面的菜单叫法随版本略有差别，F11 这个键是稳定的。至于新装环境，建议按上面那条推荐路径来；本课程后面的命令一律照命令行写，Dev-C++ 用户对照上表操作即可。

从 IDE 拷代码时，别把行号一起拷进去

从网页或课件里复制代码时，如果连左边显示的行号一起选了进来，就会编不过——那些数字会被当成代码。编辑器左边那排行号是它自己画上去的，不用你写，也不该出现在文件内容里（Learn C++ 在「编译失败怎么办」一节里专门提醒了这一点）。
