0017 · 空指针与常见陷阱

空指针与常见陷阱

本节目标：认出程序崩溃在哪一行、为什么崩，并加上判空与边界检查让崩溃消失

指针一上手，程序就开始在你毫无防备的时候闪退，屏幕上一句 Segmentation fault 就没下文了。这一课要把这几类崩溃逐个摆出来，说清每一处崩在哪、为什么崩，最后动手加一道检查，看崩溃消失。

先认识崩溃长什么样

先看一段注定要崩的程序。

存成 trap-01.cpp 再编译。这个程序里有一行被注释掉了，正是那一行会让它崩——留着不跑，是为了让这份代码能编译过：

// trap-01.cpp -- 现场一：空指针解引用之前的那个地址
#include <iostream>
using namespace std;

int main()
{
    int *p = nullptr;       // p 明确写着"我不指向任何东西"

    cout << "p 存的值是 " << p << endl;
    cout << "p 是不是空的：" << (p == nullptr) << endl;

    // 下一行就是崩溃点，这里先注释掉：
    // cout << *p << endl;      // 顺着地址 0 去取数据 → 段错误

    cout << "程序活着走到这里" << endl;
    return 0;
}
$ g++ trap-01.cpp -o trap-01
$ ./trap-01
p 存的值是 0x0
p 是不是空的：1
程序活着走到这里

nullptr 是空指针：值为 0 的指针，表示「不指向任何有效对象」。nullptr 是 C++ 里统一用的写法，老代码里还会看到 NULL 和 0，本课程一律用 nullptr。

解引用一个空指针是未定义行为：语言标准对「这时应该发生什么」不作任何规定，编译器也不需要保证什么。实际运行中它多半会让程序崩掉——地址 0 不属于你的程序，操作系统会拦下这次访问——但这句话要说准：标准给的结论是「未定义」，不是「必然崩」。崩掉只是它在常见实现上最常见的表现。

把注释那行放开，就得到这一次的崩溃现场：

$ g++ trap-01.cpp -o trap-01
$ ./trap-01
p 存的值是 0x0
p 是不是空的：1
zsh: segmentation fault  ./trap-01
崩溃提示在不同系统上长得不一样

Segmentation fault（段错误）是说：程序试图访问一块它没有权限访问的内存。地址 0 属于这一类，所以顺着 nullptr 去取数据几乎总是当场结束。

提示文字与退出码随平台而异：

  • macOS / Linux：终端会打印 Segmentation fault 或 zsh: segmentation fault ./trap-01，退出码 139；
  • Windows / MinGW（Dev-C++、VS Code 里的 g++）：程序往往直接闪退，什么都不打印，窗口一闪就没了。

未定义行为的意思是：结果不由标准规定，换一台机器、换一个编译选项，现象就可能不一样。看到崩溃提示能对上这里的描述就够了，不必因为细节不同而怀疑自己的代码。

在 Windows 上遇到「运行了但什么都没输出、窗口直接关掉」，先怀疑是不是崩了，而不是怀疑自己的代码没写对。

野指针：没初始化的指针里是什么

空指针至少有个明确的值 0，出问题的地方看得见。野指针更麻烦一点：它是声明了却没有赋值的指针，里面装的是什么完全不知道。

存成 trap-02.cpp 再编译：

// trap-02.cpp -- 现场二：野指针——没初始化的指针里是什么
#include <iostream>
using namespace std;

int main()
{
    int *p;                 // 只说了"p 是个能存地址的变量"，没给地址

    cout << "p 里现在装着 " << p << endl;
    cout << "第二次运行，这个数又会不一样" << endl;

    return 0;
}
$ g++ trap-02.cpp -o trap-02
$ ./trap-02
p 里现在装着 0x1f4418018
第二次运行，这个数又会不一样

打印出来的是一个随机的地址，每次运行都可能不同。这一段代码把这件事说明白了：int *p; 只声明了「p 能存一个 int 的地址」，没有给它任何地址，它里面是刚才那块内存上残留的字节。

野指针为什么危险？因为解引用它会去访问一个随机的地址。这个地址可能恰好指向程序自己能访问的地方，那就悄悄改坏了别的数据；也可能指向别人的地盘，那就当场崩。

$ ./trap-02
Bus error: 10

在 macOS 上野指针解引用常见的表现是 Bus error（总线错误），Linux 上多半是 Segmentation fault，Windows 上还是闪退。名字不同，原因都是「访问了一个不该访问的地址」。

一种容易误认的写法

存成 trap-07.cpp 再编译：

// trap-07.cpp -- 反例：把没初始化的指针直接传出去用
#include <iostream>
using namespace std;

int main()
{
    int *p;
    *p = 90;                // p 里还不知道是什么地址，就往那儿写数据
    cout << *p << endl;
    return 0;
}

编译器会给出警告 variable 'p' is uninitialized when used here，并建议写成 = nullptr。这类警告出现时不要跳过——它指出的正是后面那次崩溃。养成习惯：指针声明时就给它一个值，还不知道指哪儿就先写 nullptr。

悬空指针：指的地方已经不属于你了

第三种情况更隐蔽：指针曾经指向一个有效的变量，后来那个变量没了，指针还留着那个地址。

先看一个能编译过、也能跑出结果的版本。

存成 trap-04.cpp 再编译：

// trap-04.cpp -- 现场三：指针指着的变量已经出了作用域
#include <iostream>
using namespace std;

int main()
{
    int *p = nullptr;

    {
        int score = 87;         // score 只活在这对花括号里
        p = &score;             // p 记住了它的地址
        cout << "花括号里面，*p = " << *p << endl;
    }                           // 到这里 score 就没了

    cout << "花括号外面，p 里还存着 " << p << endl;
    cout << "但它指的那块地方已经不属于这个程序了" << endl;

    return 0;
}
$ g++ trap-04.cpp -o trap-04
$ ./trap-04
花括号里面，*p = 87
花括号外面，p 里还存着 0x16d76a29c
但它指的那块地方已经不属于这个程序了

score 是花括号里的局部变量。程序给这类变量划了一块专门的地方：函数一被调用，它的局部变量就在这块地方住下；函数一返回，这块地方就整体交还出去。花括号结束、函数返回，都算「用完了」。交还的意思是使用权没了，不是把字节擦掉——那块地方上的 87 通常还留在原处，下一个用这块地方的函数会把新数据写进去，覆盖掉它。

p 里存的地址还在，但它指着的地方已经不属于 score 了。这种指针叫悬空指针。

危险在于：程序不会立刻报错。p 打印出来的地址看着很正常，只要不碰它，一切如常；一旦解引用，读到的可能是别人刚写进去的数据，也可能直接崩。第 9 章讲过「函数里返回局部变量的地址」这个坑，说的就是同一件事：函数一返回，它的局部变量就交还出去了。

编译器对悬空指针能帮上一点忙。下面这个函数交回一个局部变量的地址。

存成 trap-06.cpp 再编译：

// trap-06.cpp -- 反例：指针指着的变量已经出了作用域，还想继续用它
#include <iostream>
using namespace std;

int *makePointer()
{
    int score = 87;         // score 是函数的局部变量
    return &score;          // 把它的地址交出去
}

int main()
{
    int *p = makePointer();
    cout << *p << endl;     // 函数早就结束了，那块地方已经不归 score 了
    return 0;
}

编译这个文件时，编译器会给出警告：

warning: address of stack memory associated with local variable 'score' returned

警告的名字是 -Wreturn-stack-address，意思是「你把一块马上要失效的内存的地址交出去了」。看到这行警告，就要回头检查这个指针到底还能不能用。这段代码能编译过，运行结果也不稳定——可能打印出 87，也可能打印出别的数。

越界：走到数组末尾以后

第四种是数组上的老问题。数组连续存放，指针往后走很方便，走过头也不会有人拦你。

存成 trap-03.cpp 再编译：

// trap-03.cpp -- 现场四：越界——指针走到数组末尾之后还在解引用
#include <iostream>
using namespace std;

int main()
{
    int scores[5] = {88, 76, 95, 60, 82};

    int *p = scores;
    for (int i = 0; i < 3; i++)
        p++;                    // 走三格，指向 scores[3]

    cout << "p 现在指着 " << *p << endl;     // 60，还在范围内

    cout << "再往后走一格：" << *(p + 1) << endl;   // 82，也还在范围内

    cout << "继续往后：" << *(p + 5) << endl;       // 越界了，读到的是别处的字节

    return 0;
}
$ g++ trap-03.cpp -o trap-03
$ ./trap-03
p 现在指着 60
再往后走一格：82
继续往后：1871620352

最后一行的数每次运行都不一样，因为 *(p + 5) 已经走到数组外面去了，读的是那块内存上别的东西。越界读就是这样：它不会报错，只会给你一个看不懂的数。

越界写比越界读更麻烦。

存成 trap-08.cpp 再编译：

// trap-08.cpp -- 反例：把成绩写到数组外面去了
#include <iostream>
using namespace std;

int main()
{
    int scores[5] = {88, 76, 95, 60, 82};

    for (int i = 0; i <= 5; i++)     // i 从 0 到 5，一共 6 次
        scores[i] = 100;             // 最后一次写的是 scores[5]，那格不属于这张表

    cout << "循环跑完了，程序看着没事" << endl;
    for (int i = 0; i < 5; i++)
        cout << scores[i] << " ";
    cout << endl;

    return 0;
}
$ g++ trap-08.cpp -o trap-08
$ ./trap-08
循环跑完了，程序看着没事
100 100 100 100 100

边界写成 i <= 5 之后循环跑了 6 次，最后一次写的 scores[5] 不在这张表里。这个程序跑完了、看着没事，别处的数据已经被改掉了——第 10 章讲「数组越界不报错却能跑」，就是这种情形。要等很久以后某次打印出一个奇怪的数，才会发现这里出了问题。

判空与边界检查：让崩溃消失

四类问题各有各的成因，防的办法却很统一：在解引用之前先问一句「这个地址能用吗」。

  • 空指针：用 p == nullptr 判断，空的就不进函数体；
  • 边界：把长度一起传进来，用 i < n 而不是写死的数字；
  • 野指针：声明时就写 int *p = nullptr;；
  • 悬空指针：不要让指针活过它指的那个变量。

存成 trap-05.cpp 再编译：

// trap-05.cpp -- 加一道判空检查，崩溃消失
#include <iostream>
using namespace std;

int highest(const int *p, int n)
{
    if (p == nullptr || n <= 0)     // 先问清楚：这张表到底存不存在
        return -1;                  // 没有成绩表，就交回一个说得清的标志

    int top = p[0];
    for (int i = 1; i < n; i++)
        if (p[i] > top)
            top = p[i];
    return top;
}

int main()
{
    int scores[5] = {88, 76, 95, 60, 82};

    cout << "正常调用：" << highest(scores, 5) << endl;
    cout << "交一张不存在的表：" << highest(nullptr, 5) << endl;
    cout << "交一张空的表：" << highest(scores, 0) << endl;
    cout << "三种情况都打印完了，程序没有崩" << endl;

    return 0;
}
$ g++ trap-05.cpp -o trap-05
$ ./trap-05
正常调用：95
交一张不存在的表：-1
交一张空的表：-1
三种情况都打印完了，程序没有崩

把 if (p == nullptr || n <= 0) return -1; 这一行删掉，第二次调用 highest(nullptr, 5) 就会在 int top = p[0]; 那一行崩掉。加回来，三种调用都能走完。这就是「加了判空之后崩溃消失」的可观察变化。

两个条件都要写：p == nullptr 挡住「表不存在」，n <= 0 挡住「表是空的」。少了后面那一条，p[0] 照样是越界读。

两种写错的方式

前面四类陷阱是地址本身出了问题，还有两类是「把指针和它指向的东西弄混」。这两种都不会崩，只会让程序做的事跟你以为的不一样。

第一种：把 p 和 *p 写反了。

存成 trap-09.cpp 再编译。这个程序故意写错，用来看看编译器会说什么：

// trap-09.cpp -- 反例：把 p 和 *p 弄混了
#include <iostream>
using namespace std;

int main()
{
    int score = 60;
    int *p = &score;

    p = 100;        // 想给成绩满分，写成了给指针赋值

    cout << score << endl;
    return 0;
}

编译这行代码会失败：

error: incompatible integer to pointer conversion assigning to 'int *' from 'int'

这个错拦得好。p = 100 的意思是「让 p 指向地址 100」，地址 100 上没有 score。要改成绩，得写 *p = 100;——先解引用回到那间屋子，再改里面的东西。

第二种：以为指针往前走了一格，其实数据的值被改了。

存成 trap-10.cpp 再编译。这个程序故意写错：

// trap-10.cpp -- 反例：以为在遍历，其实在改数据
#include <iostream>
using namespace std;

int main()
{
    int scores[4] = {88, 76, 95, 60};
    int *p = scores;

    for (int i = 0; i < 4; i++)
        (*p)++;                 // 每一轮都是把 scores[0] 加一，p 一直没动

    cout << "走完之后 p 指着 " << *p << endl;
    for (int i = 0; i < 4; i++)
        cout << scores[i] << " ";
    cout << endl;

    return 0;
}
$ g++ trap-10.cpp -o trap-10
$ ./trap-10
走完之后 p 指着 92
然后成绩表：92 76 95 60

这个程序跑完不崩，四个成绩里的第一个从 88 变成 92，后面三个没动——循环跑了四遍，每一遍都在改同一个元素。要遍历就该写 *p++ 或者 p[i]。

这两处和上一课 parr-04.cpp 里的 *p++ 与 (*p)++ 是同一件事，放在崩溃这一章再对一遍，是因为它们不崩、最容易留下来。

把崩溃变成能看懂的现象

最后把四类问题放在一张表里对一遍。表格里的「怎么发现」一列，写的是遇到它时的第一条线索。

陷阱长什么样为什么会这样怎么发现
空指针一到那一行就崩（Windows 上是直接闪退）顺着 0 号地址取数据，那里不许访问打印 p，看到 0x0
野指针有时崩、有时悄悄改坏数据指针没初始化，里面是随机地址编译警告 uninitialized
悬空指针换台机器、换个编译选项结果就变了指向的变量已经出了作用域警告 -Wreturn-stack-address
越界打印出一个莫名其妙的数走到数组外面，读写了别人的内存检查循环边界是 < n 还是 <= n

再加一条经验：崩溃时第一件事是看它在哪一行崩。把程序里每一处解引用前面都加一句打印，输出停在哪一句之后，问题就在下一句。

然后再把它注释回去，确认程序又能正常跑完。

练习 第 2 步 · 把判空检查删掉再装回来

在 trap-05.cpp 里把 if (p == nullptr || n <= 0) return -1; 这一行删掉，编译运行，看程序在第几个打印之后崩。然后把这一行装回去，再跑一遍，确认三种调用都能打印完。

练习 第 3 步 · 改成边界检查

把 trap-08.cpp 的循环边界从 i <= 5 改成 i < 5，重新编译运行，确认打印出来的还是五个成绩。再写一个版本：循环写成 for (int i = 0; i < n; i++)，其中 int n = sizeof(scores) / sizeof(scores[0]);，让边界跟着数组长度走。
